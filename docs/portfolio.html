Sample 1 · Engineering tutorial

Eliminating query timeouts on a multi-tenant SQL Server

Audience: backend engineers. Goal: explain a real fix so a reader can apply it themselves.

A report that ran in milliseconds during testing started timing out in production. Nothing had changed in the code — only the data had grown, and dozens of tenants now shared the same tables. Here is how we brought that query back under a second, without new hardware.

1. Read the plan before touching anything

The first step is never a guess. We captured the actual execution plan and looked for the usual suspects: a clustered index scan over the full table and a stack of key lookups. Translation: SQL Server was reading every tenant's rows to answer a question about one.

2. Index for the query you actually run

A single-column index on TenantId wasn't enough. The query filtered by tenant and a date range, then returned a handful of columns. So we built a composite index that matched that shape — key columns in filter order, with the returned columns INCLUDEd so the query never leaves the index:

CREATE INDEX IX_Invoice_Tenant_Date
  ON Invoice (TenantId, CreatedDate)
  INCLUDE (Status, Total);

The scan became a seek, and the key lookups disappeared.

3. Page inside a temp table, not across the big join

The report joined several large tables and then paged the result. Applying OFFSET / FETCH to that whole join forced SQL Server to build the entire set every time. Instead, we resolved the page of IDs first into a temp table, then joined only those rows back to the detail tables:

SELECT InvoiceId INTO #page
FROM Invoice
WHERE TenantId = @tenant AND CreatedDate >= @from
ORDER BY CreatedDate DESC
OFFSET @skip ROWS FETCH NEXT @take ROWS ONLY;

-- then join #page (tiny) to the detail tables

4. Keep writes short and locked at the row

Concurrent tenants were also blocking each other. Wrapping the write path in short transactions with row-level locking (rather than letting SQL Server escalate to a table lock) removed the contention.

Result

Query time dropped from repeated timeouts to consistently under a second, and it stayed there as data kept growing. No extra servers — just reading the plan and indexing for the real workload.

WHY THIS WORKS

Leads with the reader's pain, gives one idea per section, and pairs each claim with copy-pasteable SQL. A busy engineer can skim the headings and still leave knowing exactly what to do.

Sample 2 · API reference

Issue an e-invoice

Audience: developers integrating a billing/e-invoice API. Goal: everything needed to make the call correctly on the first try.

Creates and submits an e-invoice to the tax authority, and returns a signed, legally valid document. Idempotent on clientRef.

POST /api/v1/invoices
Authorization: Bearer <token>
Content-Type: application/json

Request body

FieldTypeRequiredDescription
clientRefstringYesYour unique reference. Re-sending the same value returns the original invoice instead of creating a duplicate.
buyer.taxCodestringYesBuyer's tax identification number.
items[]arrayYesLine items — name, qty, unitPrice, taxRate.

Example

curl -X POST https://api.example.com/api/v1/invoices \
  -H "Authorization: Bearer $TOKEN" \
  -d '{ "clientRef": "SO-10231",
        "buyer": { "taxCode": "0101234567" },
        "items": [{ "name": "License", "qty": 1,
                    "unitPrice": 200, "taxRate": 10 }] }'
{ "invoiceId": "INV-2026-000512",
  "status": "issued",
  "pdfUrl": "https://.../INV-2026-000512.pdf" }

Errors

CodeMeaningFix
422Invalid tax codeVerify buyer.taxCode against the tax registry.
409Duplicate clientRefSafe to ignore — the original invoice is returned.
503Tax authority unavailableRetry with back-off; the call is idempotent.
WHY THIS WORKS

The 409 and 503 rows answer the two questions every integrator asks in production — "will I double-charge?" and "what if their service is down?" — before they have to ask support.

Sample 3 · Feature note / README

Ship on every push: the shopvot pipeline

Audience: developers evaluating a demo repo. Goal: explain what happens on git push in 20 seconds.

shopvot deploys itself. Push to main and a self-hosted GitHub Actions runner does the rest — no manual steps, no downtime.

git push  ─▶  build multi-stage Docker image
          ─▶  health-check the new container
          ─▶  rolling replace (old stays up until new is ready)
          ─▶  live, 24/7

If the health check fails, the old container keeps serving and the deploy stops — so a bad build never takes the site down. The whole flow is built from source and runs on a single machine.

WHY THIS WORKS

A diagram carries the whole story before the prose does, and the one line that matters to a cautious reader — "a bad build never takes the site down" — is stated plainly, not buried.
